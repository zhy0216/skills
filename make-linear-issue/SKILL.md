# Make Linear Issue

扮演一位资深、经验丰富的产品经理：理解产品定位与用户任务，找出有证据支撑的功能缺口，权衡用户价值与交付成本，将需求写成团队可以评估、开发和验收的 Linear issues。

交付物是 Linear 中的需求：**本次新建 issue 全部进入 Backlog，每条都设置原生 priority；存在前置依赖时，在描述中说明并建立 Linear 原生阻塞关系。** 探索以读取仓库和需求资料为主，不实施功能或修改业务代码。

## 输入与两种模式

`args` 是可选的产品方向或需求 prompt，也可以来自当前对话；用户最新的明确指令优先。Team、Project、数量等提交偏好不算产品方向。

- **没有 prompt**：系统探索整个 repo，理解产品全貌并发现功能缺口。不要因为没有 prompt 而要求用户先提供需求。
- **有 prompt**：先将 prompt 转换为目标用户、待完成的任务、期望结果和范围，再沿该方向探索相关用户旅程、上下游能力及必要前置条件。读取全局上下文，但避免把无关方向塞进本次 issues。

普通产品假设采用合理默认并注明。缺失信息会改变产品方向或导致投错 Team 时，提出一个具体问题，同时继续不依赖答案的探索。用户已要求提单时，准备完整内容后直接创建，不重复索要逐条确认；用户明确只要草稿时遵守该范围。

调用示例：

```text
$make-linear-issue
$make-linear-issue 探索新用户从首次使用到完成核心任务之间缺失的功能
$make-linear-issue 围绕团队协作探索，提交到指定 Team 的现有 Project
```

## 1. 建立产品与仓库认知

先读取适用的 `AGENTS.md` / `CLAUDE.md`、README、产品文档、roadmap、包配置和目录结构，用 `rg --files`、`rg` 定位代码，再追踪实现。区分产品承诺、当前实现和未来设想。

建立简要产品地图：服务谁、解决什么任务、核心价值是什么、主要入口与模块、关键业务对象及生命周期。CLI、SDK、开发者工具、skill 仓库也按真实使用者和工作流分析；不要默认每个产品都需要登录、付费或团队协作。

全仓模式先列出每个自有应用、一级模块和 workspace 包，维护一张简短的探索覆盖表：`模块 / 用户旅程 / 已检查的入口与实现 / 当前能力 / 缺口或待验证项`。覆盖所有自有模块；跳过第三方依赖、生成代码和构建产物。大型仓库先完成广度覆盖，再深入有信号的路径；记录无法访问、无法运行或尚未深入验证的部分。

沿真实路径检查适用的产品环节：

- **开始使用**：发现入口、初始化、导入已有数据、示例与首次取得价值。
- **完成核心任务**：创建、查找、查看、编辑、组织、输出和后续处理是否形成闭环。
- **管理与协作**：角色、分享、交接、权限和多用户场景是否满足产品已有定位。
- **持续使用**：状态反馈、进度、历史记录、再次进入任务和重复操作。
- **异常与退出**：空状态、错误恢复、取消、撤销、删除、导出和其他必要生命周期操作。
- **产品表面一致性**：UI、API、CLI、SDK、文档声明之间是否存在影响用户任务的能力缺口。

以上是检查视角，按产品适用性取舍。代码质量、依赖升级、测试覆盖率等工程发现，只有在它们直接阻止目标用户能力时才纳入本次产品需求。

## 2. 验证缺口，形成候选需求

每个候选都回答：**哪个用户，在什么场景，当前无法完成什么；补齐后得到什么价值；依据是什么。** 优先关注核心任务断点、只有一半的功能、缺失的生命周期操作，以及已有能力难以发现或无法组合使用的问题。

验证时交叉检查入口、调用链、服务端行为、数据模型、相关测试和文档。搜索无结果或单个 `TODO` 只能作为线索；继续检查其他入口、配置控制、外部系统承接或有意排除的能力。文档与代码冲突时写明冲突。必要时运行已有的局部验证或体验流程；未运行的行为标注为静态分析推断。

候选记录至少包括：

- 目标用户、触发场景、当前障碍或替代办法、预期用户价值。
- 已实现部分与具体缺口；附仓库相对路径和行号、相关符号或文档位置。可生成可靠源码链接时附链接。
- 最小可交付范围、可观察的验收标准，以及影响判断的假设。
- 建议 priority、排序理由、前置依赖及证据置信度。

将观察事实与产品判断分开：`已确认` 表示有明确实现或运行证据，`有依据的推断` 要说明搜索范围及不确定性，`待验证设想` 不直接包装成功能开发 issue。需求证据不足但验证本身有明确价值时，可创建有具体研究问题、验证方式和决策产出的探索 issue，并明确其类型。

按可独立交付和验收的用户结果拆分；同一结果所需的 UI、API、数据变更通常属于同一 issue。过大的方向拆成有价值的递进切片，需要时使用父子 issue；父子层级与前置依赖分别处理。

默认提交所有经过验证、符合范围且不重复的候选，不设置凑数或任意截断的条数。低价值猜想留在探索结论中；没有可信缺口就如实报告，不为创建 issue 而编造需求。用户指定数量时按优先级选取，并说明必要前置项是否已包含。

## 3. 确定 Linear 目标并去重

优先使用当前环境可用的 Linear MCP / connector，先读取实际工具 schema。常用能力是 `list_teams`、`list_projects`、`list_issue_statuses`、`list_issues`、`get_issue` 和 `save_issue`；环境可能使用不同前缀或创建 / 更新工具名，以实际接口为准。

目标选择优先级：用户明确指定 → 当前对话已确认的映射 → 仓库配置、Linear 链接及项目资料中可验证的映射。通过可用 Team / Project 数据验证归属。只有一个可用 Team 时可采用它；Project 仅在有明确匹配时设置。存在多个合理 Team 或用户指定的 Project 无法确定时，及时询问投放目标，同时继续完成候选草稿，不凭仓库名称猜测。

读取目标 Team 的 **issue workflow statuses**，选取类型为 `backlog` 的实际状态 ID；优先用户指定的 Backlog 状态，其次名为 Backlog 的状态或该类别中的明确默认项。多个状态仍有歧义时询问。不要使用 Project 的 Backlog 状态代替 issue 状态，也不要依赖新建默认值；Triage、Todo、In Progress 都不满足本 skill 的 Backlog 要求。无法确认 Backlog 状态时保留完整草稿并说明所需信息。

创建前逐项搜索已有 Linear 需求：

- 用用户问题、业务实体、能力名称及同义表达搜索，结合目标 Team / Project；对共享能力按需检查相关 Team / Project。
- 读取候选重复项的描述、状态和关系后比较范围；搜索有后续页时继续查看相关结果，不将第一页无匹配等同于不存在。
- 未完成 issue 已覆盖同一用户问题与验收范围时，引用并跳过新建，记录其原状态；不会为了统一 Backlog 而移动或重排已有 issue。
- 部分重叠时仅为可独立验收的增量创建 issue，写明与已有 issue 的边界。已完成、取消或归档的记录也需结合现有代码和关闭原因判断，避免重新提交已交付或明确放弃的需求。
- 同时检查本次候选之间的重复和范围重叠。

未连接 Linear、权限不足或目标尚未确定时，继续完成探索、优先级、依赖分析和可提交草稿，明确哪些查询尚未完成；恢复访问后先完成目标验证和去重再提交。不要声称草稿已创建，也不要改投其他平台。

## 4. 设置优先级与依赖

每个新建 issue 都填写 Linear 原生 `priority`，描述中同时写出理由。使用以下数值，不把 P0 / P1 等自定义编号直接当作 API 值：

| Linear priority | 数值 | 产品判断 |
| --- | --- | --- |
| Urgent | 1 | 有明确时效或严重用户阻塞证据，延后将直接造成重大损失；常规探索很少使用。 |
| High | 2 | 核心用户任务无法闭环、关键角色无法完成主要操作，或明确阻塞重要已承诺能力。 |
| Medium | 3 | 有清晰用户价值的功能补全，存在可接受的替代路径；一般功能缺口的默认起点。 |
| Low | 4 | 适用范围较窄、使用频率较低或属于次要便利性提升，仍有可说明的用户价值。 |

`0` 是 No priority，本 skill 不使用。结合目标用户覆盖、任务影响、使用频率、时效、依赖解锁价值、成本与证据强度排序；未知数据写未知，不编造用户量、收入、转化率或精确 RICE 分数。**优先级与状态独立，Urgent 也必须进入 Backlog。**

依赖规则：

- **硬依赖**：缺少 A，B 就无法交付或验收。记录 `B blocked by A`，并解释 A 提供的具体能力。
- **软关联**：同一主题、实现方便或建议先后顺序，写为关联 / 建议顺序；不要伪造阻塞关系。
- 前置能力已有未完成 issue 时引用其真实 ID；已交付能力写为现有基础，不设为阻塞。外部交付或待决策项要说明交付物与解除条件，不能编造 Linear ID。
- 尚未被跟踪的必要前置需求，纳入本次候选并同样验证、去重和定优先级；若超出用户范围或数量限制，明确标记缺失前置项，向用户说明，不能声称依赖已完整建立。
- 检查依赖图没有自依赖或循环；若出现循环，重新划分可交付边界。优先级表示价值与紧迫性，执行顺序同时服从依赖。

## 5. 编写并提交 issues

标题表达可交付的用户能力，例如“允许用户恢复误删的项目”；避免“优化体验”“完善功能”等无法验收的标题。默认使用用户的语言，保留代码符号和产品专有名称。

每条 issue 使用以下紧凑结构，内容深度与需求复杂度相称：

```markdown
## 用户问题与价值
谁在什么场景遇到什么障碍，当前替代办法及补齐后的价值。

## 当前行为与证据
已实现的部分、实际缺口、仓库路径与行号 / 符号 / 文档链接。
标明运行验证或静态推断，以及重要假设。

## 目标行为与范围
最小可交付的用户结果、必要交互和边界；明确本条不覆盖的相邻需求。

## 验收标准

- [ ] 在明确前置条件和用户操作下，产生可观察的结果。
- [ ] 与此功能相关的权限、空状态、错误恢复或其他关键边界有明确行为。

## 优先级
High / Medium / Low / Urgent；为什么是这个级别，影响和证据是什么。

## 依赖与关联
Blocked by：真实 issue 标识与链接，说明依赖的能力；没有则写“无”。
相关 issue / 建议顺序 / 外部依赖：存在时分别列出，注明原因或解除条件。

## 成功信号
如何判断用户问题已解决。已有指标就引用；没有基线时给出观察或验证方法。
```

验收条件必须描述产品行为，不以“完成前端 / 后端”“测试通过”代替。实现线索只写帮助理解约束的必要信息，不替工程团队预设无依据的技术方案。删除不适用的模板提示，将假设与开放问题落在对应段落。

提交流程：

1. 准备完整候选内容、priority、目标 Team / 可选 Project、Backlog 状态及依赖图；完成上述验证后直接进入创建。
2. 按依赖顺序先建前置 issue，再建依赖它的 issue；每次创建显式传入 `team`、`title`、`description`、`state` 和 `priority`。`state` 使用已查询的 Backlog 状态 ID。Project 已确认时才设置；负责人、Cycle、截止日期仅按用户指定或已有明确约定填写。
3. 记录每次返回的真实 ID、identifier、URL 和创建结果，建立“候选 → Linear issue”映射。描述中的临时编号在提交前替换为真实标识和链接。
4. 建立原生关系：例如 B 依赖 A 时，在 B 上设置 `blockedBy: [A 的 ID]`，或在 A 上设置 `blocks: [B 的 ID]`，选择一种方向即可。所有相关 issue 创建完后补全必要链接及关系；更新时遵守工具的追加 / 替换语义，保留已有关系。`relatedTo`、父子关系、描述里的链接都不能替代硬依赖。
5. 若当前工具不支持原生阻塞关系，仍在描述中写清真实 issue 链接、依赖方向和原因，并在结果中明确“原生关系未设置”；可用且已授权的 Linear 接口支持时完成补设，不假装已建立。
6. 逐条核对 Team、Project、实际 Backlog 状态、非零 priority 和依赖方向；创建 / 更新响应不足以确认这些字段时，使用 `get_issue` 并包含 relations 读回核实。本次新建项存在偏差时修正后复核；遇到权限限制或自动化反复改回时停止重试，报告具体未达标项。

创建请求超时或返回结果不明确时，先通过标题、内容、目标和最近创建记录核实是否已成功，避免盲目重试产生重复。部分成功时保留成功映射，只继续未完成项；不能判断某次写入是否成功时停止该项重试并报告。Markdown 通过结构化参数传入，保留真实换行。

## 6. 汇报结果

简要说明探索模式、产品判断与覆盖范围，然后给出结果表：`issue 标识与链接 / 标题 / 实际状态 / priority / Blocked by`。有依赖时用真实标识说明建议顺序，清楚表达谁依赖谁、哪些前置能力需要先交付。

另列已存在而跳过的需求、待验证设想、尚未覆盖的模块，以及创建或关系设置未完成的项目。没有创建时说明原因；只把服务端确认存在的 issue 报为已创建。草稿保留完整提交字段、验收标准和临时依赖映射，以便恢复后继续。

Linear 状态与关系的官方说明可在接口含义不清时查阅：[Issue status](https://linear.app/docs/configuring-workflows)、[Issue relations](https://linear.app/docs/issue-relations)。
